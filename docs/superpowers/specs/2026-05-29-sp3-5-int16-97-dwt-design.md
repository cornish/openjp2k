# SP-3.5 — Int16 9/7 DWT Path for ≤12-bit Precision (Lossy)

## Goal

Add an int16 fixed-point path to the inverse 9/7 (irreversible / lossy)
DWT in `src/lib/openjp2/dwt.c` for components with input precision ≤ 12
bits, whole-tile decode only. Targets the largest unaddressed
lossy-decode opportunity after D8: the SP-2.1a post-D8 profile localized
13% of single-thread runtime on 1024² 8-bit lossy WSI tiles to the
float-AVX2 9/7 inverse DWT (vs grok's 5.6% in the same role using a
16-bit Highway implementation).

Halves SIMD lane width (8 float lanes → 16 int16 lanes per `__m256i`) →
2× throughput on the dominant kernel. Predicted: WSI 1024² 8-bit lossy
moves from current +3.33% vs grok at t=8 to ~+5-6% vs grok; 8-bit lossy
iter slice gains +5-8% on top of D8.

This is **SP-3.5** — the 9/7 analogue of SP3.2's 5/3 int16 work. AVX2
only, gated by `OPJ_ENABLE_AVX2`. Departs from the project's byte-exact
SIMD pattern: 9/7 lift coefficients are real-valued, so a Q-format
fixed-point implementation introduces small rounding deltas vs the float
reference. Acceptable for lossy decode per the JP2K spec; the cleanroom
research (`docs/grok-cleanroom-research/grok-int16-97-dwt.md`) notes
~0.5 dB peak SNR loss on typical content — i.e. PSNR far above any
reasonable floor.

## Background

The inverse 9/7 (irreversible) DWT in `dwt.c` currently has an
`__AVX2__`-gated float-lift path from SP3.1. It operates on `__m256`
containing 8 float32 elements per vector, applying the canonical lift
formulas:

```
s'[i]  = s[i] + δ × (d[i-1] + d[i])         /* undo update 2 */
d'[i]  = d[i] + γ × (s'[i] + s'[i+1])       /* undo predict 2 */
s''[i] = s'[i] + β × (d'[i-1] + d'[i])      /* undo update 1 */
d''[i] = d'[i] + α × (s''[i] + s''[i+1])    /* undo predict 1 */
out_low[i]  = K   × s''[i]                  /* scale */
out_high[i] = 1/K × d''[i]
```

with T.800 Annex F coefficients α=-1.586134342, β=-0.052980118,
γ=0.882911075, δ=0.443506852, K=1.230174105, 1/K=0.812893066.

## Design

### Activation

At `opj_dwt_decode_real` entry, gate on the source component's
precision and the `whole_tile_decoding` flag, mirroring SP3.2's
activation pattern. The current public entry is:

```c
OPJ_BOOL opj_dwt_decode_real(opj_tcd_t *p_tcd, opj_tcd_tilecomp_t* tilec,
                             OPJ_UINT32 numres)
{
    if (p_tcd->whole_tile_decoding) {
        return opj_dwt_decode_tile_97(p_tcd->thread_pool, tilec, numres);
    } else {
        return opj_dwt_decode_partial_97(tilec, numres);
    }
}
```

SP-3.5 inserts an AVX2-gated int16 fork on the `whole_tile_decoding`
branch:

```c
OPJ_BOOL opj_dwt_decode_real(opj_tcd_t *p_tcd, opj_tcd_tilecomp_t* tilec,
                             OPJ_UINT32 numres)
{
    if (p_tcd->whole_tile_decoding) {
#ifdef __AVX2__
        const OPJ_UINT32 compno = (OPJ_UINT32)(tilec -
                                  p_tcd->tcd_image->tiles->comps);
        const opj_image_comp_t *image_comp = &p_tcd->image->comps[compno];
        if (image_comp->prec <= 12) {
            return opj_dwt_decode_tile_97_int16(p_tcd->thread_pool,
                                                tilec, numres);
        }
#endif
        return opj_dwt_decode_tile_97(p_tcd->thread_pool, tilec, numres);
    } else {
        return opj_dwt_decode_partial_97(tilec, numres);    /* unchanged */
    }
}
```

Per-tilec check matches SP3.2; mixed-precision multicomponent images
dispatch each component independently. Partial-tile / ROI decode
always uses the float path (per SP3.2b's negative-result lesson and
the cleanroom doc's documented grok gate).

### Q-format and the multiply primitive

All intermediate scratch state is **`int16_t` in Q1.15**. The single
multiply primitive is rounding multiply-high:

```
opj_q15_mul(a, b) = (int16_t)(((int32_t)a * (int32_t)b + (1 << 14)) >> 15)
```

implemented in AVX2 as `_mm256_mulhrs_epi16` (VPMULHRSW), one
instruction, hardware-rounded. The `+ 2^14` is round-to-nearest; the
`>> 15` strips the Q1.15 scale. The same primitive exists as
`vqrdmulhq_s16` on NEON, so a future Highway / NEON port (SP-3.4)
reuses the algorithmic shape.

The Q1.15 multiply can only represent factors with `|c| < 1.0`.
Coefficients with `|c| ≥ 1.0` (namely α, K, 2/K) are handled by
additive decomposition (see "Per-step strategies" below), not by
widening the Q-format.

There is **no `MULHRS_Q14` macro**. The earlier draft of this spec
proposed one; it was mathematically incorrect (doubling a rounded
Q1.15 mulhrs does not yield Q2.14 semantics because the rounding is
performed at the Q1.15 boundary, not the Q2.14 boundary). The fix is
not a different Q-format but a different decomposition — see step 0
below.

### Standard coefficient values (Q1.15 encodings)

All encodings are mechanical Q1.15 encodings of the standard T.800
coefficients (or of their decompositions). They are mathematical
facts, not tuned constants.

| name | source value | Q1.15 int16 |
|---|---:|---:|
| `Q15_DELTA`   | δ = +0.443506852                  | 14533 |
| `Q15_GAMMA`   | γ = +0.882911075                  | 28931 |
| `Q15_BETA8`   | β × 8 = +0.423840944 (note ×8)    | 13890 |
| `Q15_ALPHA_F` | |α| − 1 = +0.586134342 (fractional) | 19205 |
| `Q15_K_F`     | K − 1 = +0.230174105              | 7542  |
| `Q15_INVK_F`  | (2/K) − 1 = +0.625732422          | 20506 |

These are the only fixed-point constants the int16 path needs. The
sign of α and β in inverse synthesis becomes additive (negative
analysis coefficient → positive synthesis update), so `Q15_ALPHA_F`
is stored as a positive value and combined with addition.

### Per-step decomposition strategies

The four synthesis lift steps each use a different strategy. The
scratch buffer holds one row (horizontal pass) or `LANES` columns
(vertical pass) of int16 samples in interleaved low/high subband
order after the interleave phase.

**Step 3 — undo δ (Q1.15 direct, sum-first):**
```
S[n] -= opj_q15_mul(D[n-1] + D[n], Q15_DELTA)
```
Neighbors are summed in int16 first (one ADD) then a single mulhrs.

**Step 2 — undo γ (Q1.15 direct, sum-first):**
```
D[n] -= opj_q15_mul(S[n-1] + S[n+1], Q15_GAMMA)
```
Same shape as step 3, with γ.

**Step 1 — undo β (precision-boosted ×8, multiply-first):**
β ≈ 0.053 is small; direct Q1.15 wastes ~4 bits of magnitude. Encode
β × 8 instead, multiply each neighbor separately, sum, round, then
right-shift by 3 to cancel the ×8:
```
S[n] += (opj_q15_mul(D[n-1], Q15_BETA8) + opj_q15_mul(D[n], Q15_BETA8) + 4) >> 3
```
Because each neighbor is multiplied separately, this step does not
form an int16 sum of two neighbors and is excluded from the BIBO
sum-first headroom analysis (§ Headroom).

**Step 0 — undo α (additive decomposition, sum-first):**
|α| = 1.586 > 1, so direct Q1.15 is impossible. Decompose as
`|α| = 1 + (|α| − 1) = 1 + 0.586`:
```
sum  = S[n-1] + S[n+1]                       /* int16 */
frac = opj_q15_mul(sum, Q15_ALPHA_F)
D[n] += sum + frac
```
The integer part (×1) is applied by adding `sum` directly; only the
fractional part (×0.586) uses the multiply primitive. This eliminates
the need for any Q2.14 path.

**K and 1/K — fused into the interleave phase:**
Apply each as `x × c = x + opj_q15_mul(x, (c − 1)_q15)`:
```
x × K    = x + opj_q15_mul(x, Q15_K_F)
x × 2/K  = x + opj_q15_mul(x, Q15_INVK_F)
```
Done while gathering each subband row/column from the strided band
buffer into the contiguous scratch buffer — even samples scaled by
K, odd by 2/K. No separate scaling pass. (Note: the inverse 9/7 in
canonical form uses `1/K` on the high band; the cleanroom doc folds
the factor-of-2 from the subband normalization into the constant,
yielding `2/K`. Re-derivation in the implementation should confirm
which form matches openjp2k's pre-DWT band layout.)

### Headroom and downshift

The 9/7 has low BIBO gain. Cumulative 1D gains from subband to
reconstructed pixel (cleanroom §4):

```
gain_l[]:  1.000, 1.380, 1.333, 1.307, 1.303, …
gain_h[]:  1.298, 1.313, 1.276, 1.235, 1.231, …
```

2D worst case (level 1): `1.380² ≈ 1.90` — only ~1 bit of growth.
Sum-first steps (3, 2, 0) momentarily double the input magnitude at
the intermediate sum, doubling the worst-case transient.

Per-precision downshift requirement:

| input precision | `headroom_downshift` |
|---|---|
| 8-bit  | 0 |
| 10-bit | 0 |
| 12-bit | 0–1 |
| 14-bit | 1–2 (out of scope) |

**Mechanism.** Subband inputs are right-shifted by
`headroom_downshift` bits during the interleave phase. After the
final synthesis level, output is left-shifted by the same amount
before the DC shift / clamp. The precision loss is 1–2 LSBs per
shift step, negligible against quantization noise for lossy decode.

At the 8-bit slice that motivates SP-3.5 the mechanism is dormant
(`headroom_downshift = 0`), but the plumbing must exist because the
gate is precision ≤ 12, and 12-bit content may require a 1-bit
downshift. The implementation derives `headroom_downshift` once at
orchestrator entry from the component precision.

### Edge handling

Symmetric mirror at row/column boundaries:

- when `i == 0`, the "previous" neighbor is `scratch[i+1]`
- when `i + 1 == length`, the "next" neighbor is `scratch[i-1]`

Special-case `length == 1`: emit a single sample scaled by K or 2/K
according to parity, skip all four lift steps.

`parity` is the parity of the first output row/column index — i.e.
whether output sample 0 is even (low-pass) or odd (high-pass) in the
subband decomposition. The horizontal and vertical kernels both
take a parity argument from the per-resolution decomposition state.

### Final-level fused DC shift and clamp

At the deepest (final) synthesis resolution only, the scatter phase
is replaced by a fused DC-shift + clamp:

```
pixel = clamp(synth_value + dc_shift, dc_min, dc_max)
```

For N-bit unsigned input: `dc_shift = 2^(N-1)`, `dc_min = 0`,
`dc_max = 2^N − 1`. For N ≤ 12, all three constants and the result
fit in int16, so the entire pipeline stays in int16 lanes until the
final output store. Output store widens int16 → int32 into
`tilec->data` via `_mm256_cvtepi16_epi32`.

Signed input is not currently targeted for this path; the orchestrator
falls back to the float path if `image_comp->sgnd` is set.

### SIMD coverage: horizontal and vertical

Grok's int16 9/7 SIMDs only the horizontal pass; the vertical pass is
scalar in their implementation. SP-3.5 vectorizes both passes:

- **Horizontal:** 16 int16 lanes per `__m256i` operating across
  consecutive samples in a row. The strided gather in the interleave
  phase is unavoidable, but the four lift steps process 16 samples
  per vector instruction.
- **Vertical:** the scratch buffer becomes a `LANES × height` strip
  where `LANES = 16` columns are processed in parallel, one int16
  per column per lane. The strided gather in the interleave phase
  becomes a SIMD-width contiguous load (after a one-time transpose
  into the strip), and the lift steps run lane-wise.

Both kernels use the same Q1.15 algorithm — only the gather/scatter
shape differs. The vertical kernel mirrors SP3.2's
`PARALLEL_COLS_53_S16 = 32` shape; SP-3.5 vertical processes 16 or 32
columns per stripe, matching SP3.2's stride choice for cache
behavior.

### Kernel inventory (~700–900 LOC across two tasks)

Modeled after the existing SP3.1 AVX2 9/7 lift kernels and the SP3.2
int16 5/3 kernels.

| New (int16 9/7) | Mirrors / template |
|---|---|
| `opj_v16dwt_decode_step_h_int16_avx2`      | `opj_v8dwt_decode_step` (horizontal AVX2) |
| `opj_v16dwt_decode_step_v_int16_avx2`      | `opj_v8dwt_decode_step` (vertical AVX2) |
| `opj_v16dwt_interleave_h_int16_avx2`       | `opj_v8dwt_interleave_h` (fuses ×K, ×2/K) |
| `opj_v16dwt_interleave_v_int16_avx2`       | `opj_v8dwt_interleave_v` (fuses ×K, ×2/K) |
| `opj_dwt97_decode_h_func_int16`            | `opj_dwt97_decode_h_func` |
| `opj_dwt97_decode_v_func_int16`            | `opj_dwt97_decode_v_func` |
| `opj_dwt_decode_tile_97_int16`             | `opj_dwt_decode_tile_97` (orchestrator) |
| `opj_dwt_dcshift_clamp_int16_avx2`         | inlined into final-level scatter |

Plus pack/unpack helpers (modeled directly on the SP3.2 helpers):

- `opj_dwt_pack_int32_to_int16_q15` — int32 → int16 Q1.15 with
  optional `headroom_downshift` applied in the same pass.
- `opj_dwt_unpack_int16_q15_to_int32` — int16 → int32 with optional
  `headroom_downshift` reversal, used only when the final-level
  fused DC-shift + clamp path is not taken (defensive fallback).

The "lift coefficient constants" table from above lives at file scope
inside the `#ifdef __AVX2__` block near SP3.2's `VREG_S16` macros.

### Orchestrator data flow

```
opj_dwt_decode_tile_97_int16(tp, tilec, numres) {
    derive headroom_downshift from image_comp->prec
    scratch = opj_aligned_32_malloc(tilec_w * tilec_h * sizeof(int16_t))

    /* pack tilec->data into Q1.15 scratch with any required downshift */
    opj_dwt_pack_int32_to_int16_q15(scratch, tilec->data, ..., headroom_downshift)

    for (resno = 1; resno < numres; ++resno) {
        for each row:
            opj_dwt97_decode_h_func_int16(...)
        for each col-stripe (LANES at a time):
            opj_dwt97_decode_v_func_int16(...)   /* via thread pool */
    }

    /* Final level: fused DC-shift + clamp directly into tilec->data;
     * left-shift by headroom_downshift before clamp. */
    opj_dwt_dcshift_clamp_int16_avx2(tilec->data, scratch, ...,
                                     dc_shift, dc_min, dc_max,
                                     headroom_downshift)

    opj_aligned_free(scratch)
}
```

Scratch buffer is per-tilec (alloc/free at orchestrator boundaries),
matching SP3.2. Pooling via D6.1 is a follow-up if profile shows
alloc churn.

## Verification

### Conformance fingerprint snapshot

Run `OPJ_ENABLE_AVX2=ON` conformance after SP-3.5 lands. Enumerate
every NR-DEC-md5 test whose pass/fail status differs from the
pre-SP-3.5 baseline (the 8 pre-existing failures). Document each
shift in the outcome spec:

- Tests that newly fail at small rounding deltas: expected for some
  9/7 lossy files; non-blocking if the count is small (≤ 10).
- Tests that newly pass: bonus; document.
- Tests that previously passed and still pass: must match.

After the snapshot is documented, it becomes the new conformance
baseline for future deliverables.

### PSNR floor — empirical finding (Task 1a)

The original design assumed PSNR ≥ 60 dB based on a misread of grok's
"~0.5 dB peak SNR loss" claim. Grok's pipeline avoids a float
intermediate entirely: their `NarrowShiftFilter` consumes T1's int32
output directly with the band stepsize folded into Q-format scaling
(cleanroom §5.2). They never lose fractional precision.

openjp2k's Task 1a path bolts int16 on *after* T1 + float dequant, so
the pack does `lrintf(float)` and discards fractional bits. Empirically
on 8-bit lossy RGB color this caps the achievable PSNR at ~56–59 dB
(min observed 56.81 dB across a representative set). Each bit of
Q-format precision boost in the pack adds ~3 dB until boost=7 triggers
int16 overflow in the sum-first lift chain.

**Decision (2026-05-29):** accept the empirical floor. PSNR gate is
**≥ 50 dB** — well above visually-lossless for 8-bit content (~40–45 dB)
and 6+ dB below the 56.81 dB floor for safety margin. The 60 dB
"grok-class" target moves to **SP-3.5b**: a future deliverable that
folds T1 dequantization into the int16 pack, eliminating the float
intermediate and reaching ≥70 dB PSNR with byte-exact conformance.

### Conformance fingerprint and the env-var opt-in

Because the int16 path produces non-byte-identical output to the float
reference, every 9/7 lossy file that hits the path produces a different
MD5 than upstream openjpeg. Empirically that's ~45 NR-DEC files on the
current conformance suite — far above the spec's original "≤ 10 shifts"
threshold. The 45 are all expected precision diffs, not bugs.

**Decision (2026-05-29):** the int16 path is **env-var opt-in**. Default
off preserves byte-equivalence with upstream openjpeg and the existing
conformance fingerprint. Set `OPJ_DWT_INT16_97=1` to engage. The bench
harness and the PSNR test both opt in. Once SP-3.5b lands and PSNR
reaches ≥70 dB, a follow-up PR may flip the default to on with its own
conformance MD5 update.

### PSNR verification harness

**Test infrastructure design (in-process, no subprocess).** The
earlier draft of this spec proposed running a second decoder as a
subprocess to obtain the float-reference output. That design does not
fit the existing `tests/unit/` infrastructure (which builds against
exactly one libopenjp2) and would also force a second AVX2-OFF build
on every CI run.

The workable alternative is **in-process dispatch via a runtime
override**. Introduce a process-local override:

```c
/* Internal — not part of the public ABI.  Defined in dwt.c; declared
 * in opj_includes.h alongside other test-only hooks. */
extern int opj_dwt_force_float_97;   /* 0 = normal; nonzero = skip int16 */
```

The dispatch hook at `opj_dwt_decode_real` checks this flag in
addition to the precision gate:

```c
if (!opj_dwt_force_float_97 && image_comp->prec <= 12) {
    return opj_dwt_decode_tile_97_int16(...);
}
```

The PSNR test `tests/unit/test_dwt_int16_97_psnr.c`:

1. Decodes each test file with `opj_dwt_force_float_97 = 0` (int16
   path active), captures output buffer A.
2. Sets `opj_dwt_force_float_97 = 1` and re-decodes (float
   reference), captures buffer B.
3. Computes per-component PSNR between A and B, asserts ≥ 50 dB
   (empirical floor; see § PSNR floor above).

This runs in a single test binary linked against one libopenjp2,
requires no second build, and works under both AVX2-ON (where both
paths exist) and AVX2-OFF (where the test is skipped via CMake guard
because the int16 path isn't compiled in). Pattern is conventional
in the openjp2k unit tests — `test_mqc_diff` already uses an
analogous mechanism via the `OPJ_T1_FAST` environment variable.

Test files (resolved at implementation start; final list pinned in
the outcome doc):

- WSI 1024² 8-bit lossy: `wsi-tiles/1024x1024/JP2K-33003-2__T1024_c041r117.j2k`
  (the SP-3.5 motivating file).
- WSI 240² 8-bit lossy: a representative from
  `wsi-tiles/240x240/`.
- 8-bit photographic lossy from the archival corpus (if available;
  else a second synthetic).
- 8-bit ultrasound DICOM J2KR: `medical/J2KR_US1_J2KR.j2k`.
- 12-bit lossy file from corpus — exercises the upper end of the
  precision gate and validates the `headroom_downshift` plumbing.

### Build / AVX2-OFF behavior

- `OPJ_ENABLE_AVX2=OFF`: build clean, conformance unchanged from
  main pre-SP-3.5. The int16 path code is `#ifdef __AVX2__` gated;
  AVX2-OFF builds the float path only. PSNR test is omitted from
  the AVX2-OFF CMake configuration.
- `OPJ_ENABLE_AVX2=ON`: build clean, conformance fingerprint shifts
  as documented above; PSNR test compiles and passes.

### Manual byte-cmp is NOT used

Explicit departure from D8/SP3.2 pattern. PSNR replaces byte-cmp
because float vs Q1.15 fixed-point are not byte-equivalent on the
9/7 path.

## Scope Boundaries

- **Lossy (9/7) only.** Lossless (5/3) path is SP3.2 territory;
  untouched.
- **prec ≤ 12.** Higher precisions stay on the SP3.1 float-AVX2 path.
  SP-3.5b for ≥ 14-bit is a separate deliverable (needs the larger
  `headroom_downshift` values from the BIBO table and validation
  that the precision loss remains acceptable for lossy).
- **Whole-tile only.** Partial-tile / ROI 9/7 stays on float —
  SP3.2b's negative-result lesson applies. Partial decode is
  T1-dominated; DWT SIMD widening does not pay there.
- **Unsigned input only.** Signed components fall back to float.
- **AVX2 only.** Non-AVX2 builds run the existing SP3.1 float path.
  SSE2 int16 and NEON deferred. Highway runtime dispatch (SP-3.4 on
  the roadmap) is the right home for cross-target SIMD; SP-3.5 is
  the AVX2 proof-point.
- **No new build option.** Activates inside the existing
  `OPJ_ENABLE_AVX2` envelope.
- **No T1 changes.** T1 fast paths are at parity with grok.

## Risks

1. **Headroom mis-derivation at 12-bit.** If the per-precision
   `headroom_downshift` value is too small, sum-first steps may
   saturate; if too large, output precision loss exceeds the lossy
   tolerance. Mitigation: derive once from BIBO analysis at
   orchestrator entry; PSNR test includes a 12-bit file specifically
   to validate.

2. **PSNR test floor too tight.** 60 dB is a safe floor per the
   cleanroom note. If a corpus file unexpectedly drops below, the
   bug is in the implementation (likely a wrong sign on α/β
   inversion or a missed `headroom_downshift`), not in the floor
   itself. Mitigation: measure actual PSNR on 30+ files during
   implementation; investigate any < 70 dB before locking.

3. **Conformance fingerprint shift larger than expected.** Could be
   5 tests shift, could be 30. If many shift, hard to enumerate and
   justify each. Mitigation: if more than 10 tests shift, **pause
   and investigate** — likely an implementation bug.

4. **Vertical SIMD complexity overruns horizontal.** Vertical adds a
   transpose-into-strip and lane-wise step kernels. Mitigation: if
   Task 1a (horizontal) bench gate already meets the headline +5%
   8-bit lossy iter t=8 target, Task 1b (vertical) becomes optional
   incremental work.

5. **Cumulative MT amplification may exceed predictions.** D8 was
   super-linear at MT. Bonus if SP-3.5 follows.

6. **Cross-slice icache effects.** SP3.2 had a known +4% accidental
   cross-slice surprise; SP3.2b had a −1% accidental regression.
   Direction unpredictable. Mitigation: measure smoke + iter overall
   at t=1; document residue.

7. **Highway dispatch (SP-3.4) might obsolete SP-3.5.** Acceptable:
   SP-3.5 is the AVX2 proof-point; SP-3.4 can replace it with a
   portable equivalent when it lands.

## Open Questions

1. **Exact `headroom_downshift` for 12-bit.** Range is 0–1 per the
   BIBO table; pick at implementation time based on empirical

2. **Vertical kernel column count.** SP3.2 uses 32 columns per

3. **Scratch buffer pool integration.** Defer to a follow-up if

**Status:** COMPLETE and SHELVED. Both tasks landed and are correct, but

(`OPJ_DWT_INT16_97`); it is **not** enabled and was **not** merged as a perf
win. The prediction table immediately above did **not** hold.

**Commits:** Task 1a `88f9d5f5` (horizontal SIMD + scalar vertical
placeholder + orchestrator + dispatch + PSNR test); Task 1b `236056cd`
(vectorized vertical pass, `feat/sp3-5-int16-97-dwt`).

### Correctness — PASS

### Bench gate — FAILED
Measured on the bench host (Tiger Lake i7-1185G7, AVX2+AVX-512, but the

head decoder only, synthetic-iter, int16 ÷ float (>1 = int16 wins):

| slice | predicted | **actual** |
|---|---:|---:|
| 8-bit lossy iter t=8 | ≥ +5% | **−9% (0.912×)** |
| 12-bit lossy iter t=8 | ≥ +1% | **−8% (0.923×)** |
| lossy ≤12-bit overall t=1 / t=8 | — | **0.849× / 0.917×** |
| best case (d1, t=8) | — | **1.002× (parity)** |
| 16-bit lossy / lossless (control) | unchanged | 1.006× / 1.003× ✓ |

int16 never wins; it only reaches **parity at the shallowest case (1
decomposition level, 8 threads)** and degrades with depth (d5 ≈ 0.90×,
d8 ≈ 0.87× at t=8). Task 1b's vectorized vertical roughly *doubled* the
int16 path vs Task 1a's scalar vertical, so the kernel work was effective —
it just doesn't change the verdict.

### Root cause — the conversion tax (architectural, not a kernel bug)
The float 9/7 path being merely matched (not beaten) at the best case is
the tell. openjp2k's post-T1 sample pipeline is **float** (`tilec->data`
holds float bits after dequant; cleanroom §7.5). The int16 path must
therefore **pack float→int16 on entry and emit int16→float on exit** —
two extra full-tile memory passes (plus the precision_boost multiplies)
that the float path never pays. The theoretical 16-int16-lane vs
8-int32-lane advantage is consumed by (a) that conversion tax, (b) the
lift being memory-bound rather than ALU-bound (so 2× lanes ≠ 2× wall),
and (c) deep-level scalar fallback when `rw < 32`. A hybrid float-fallback
for small levels could lift d5/d8 toward the d1 number — but **d1 is
parity**, so the architectural ceiling here is break-even, not the gate.

### Why Kakadu and Grok win where this can't
Both reference fast codecs run a **natively integer** sample pipeline and
so never pay the conversion tax. Verified: Kakadu's survey docs implement
the "notionally floating point" 9/7 path in **16-bit fixed-point** for
throughput ("introduction of 16-bit data types"; "MMX processing for the
inverse DWT") [Kakadu Survey Documentation, Taubman, UNSW]. Grok's
cleanroom (§7.5) likewise consumes int16 subband data directly with no
float intermediate. openjp2k retrofits int16 onto a float pipeline; they
do not.

**Implication for the project:** the real path to Kakadu/Grok 9/7 speed is
**not** a DWT-kernel swap (proven here to top out at parity) but converting
openjp2k's post-T1 sample pipeline to native integer — a far larger,
cross-cutting change (T1 output, dequant, MCT, DWT, DC-shift all in int)
with its own precision/conformance risk. That is a separate, much bigger
project, not an SP-3.x-style profile-localized win.

### Decision / carry-over
- **Keep** the int16 9/7 code (correct, PSNR-verified, default-off). It is
  the working reference if a native-integer pipeline is ever pursued.
- **Do not enable** by default; **do not** advertise SP-3.5 as a perf win.
- Merge of `feat/sp3-5-int16-97-dwt` to main is a separate decision: it adds
  only dormant, opt-in code — defensible to merge for preservation with this
  Outcome attached, but it is NOT the planned `v0.13.0` perf-win tag.
- SP-3.5b (higher precision / partial-tile 9/7) is **shelved** — same tax.
- Grok's t=8 multi-thread lead remains the open competitive gap; the int16
  DWT retrofit is not the lever to close it.

### Follow-up (2026-06-01) — AVX2-valid re-confirmation + canonical number

The original gate above was run on a bench build that — it later turned out —
was silently compiling **both** decoder libraries **without AVX2**: the
openjp2k-bench `ExternalProject` subbuilds don't inherit the parent cache's
`-march=native`, so the numbers were only valid when an uncommitted stopgap
was applied. Fixed in openjp2k-bench `ddbba57` (pass `-march=native` into the
subbuild args under `JP2KBENCH_NATIVE`, default ON; verified vanilla=1329 /
fork=1899 `%ymm`). The gate was re-run from a clean checkout on the fixed build.

**Verdict unchanged — negative holds, and is now reproducible without the hack.**
Paired single-thread A/B of `OPJ_DWT_INT16_97` ON vs OFF (two back-to-back
openjp2k-only passes, runtime toggle, no rebuild): synthetic lossy **−7.82%**,
lossless drift-control +2.09%, public **−9.68%**, whole-corpus −7.62%,
drift-corrected lossy **−9.72%**. This matches the `0.912×` (≈ −9%) iter-t=8
gate above. If anything it is marginally *worse*: with `-march=native` now
reaching both libs, the float 9/7 competitor (incl. the v8 alignment win,
`3e1eb81a`) is properly vectorised, so the int16 conversion tax is no longer
masked by a slow float path. Firing re-confirmed directly: openjp2k is
bit-identical to the openjpeg float reference when OFF (`pm=1`) and diverges
when ON (`pm=0`, PSNR ≈ **29.9 dB** on 12-bit mono lossy — the same
high-bit-depth regime where § PSNR floor already noted 30–40 dB).

**Canonical dispatch-off shippable number (new, AVX2-valid).** The default
(dispatch-off) state benched 3-way, single-thread, paired geomean of per-file
MP/s over the common-file intersection (33 known openjpeg-failure files
excluded): openjp2k **+5.44% vs openjpeg 2.5.3** overall, **+8.70% vs grok**
(carried by public +13.60%; grok still leads ~3.9% on the controlled synthetic
sweep, so "beats grok" needs that qualifier). This is the first AVX2-valid
single-thread canonical number with all committed wins (D8, SP-3.2, the v8 9/7
alignment) actually compiled in.
